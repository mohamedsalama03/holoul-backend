# Private Documents (B4)

Documents owns private metadata, reservations, processing outcomes and deletion intent. Intake owns typed draft/revision attachments and current parent authorization. Documents imports Audit and technical infrastructure only; its `DocumentReferences` contract is implemented by Intake.

`DocumentService` metadata methods require an existing transaction with current identity/parent authorization. `DocumentOwner` is server-created and includes immutable parent, customer and customer-user identities plus the acting identity and correlation ID. Attachment creation and removal lock the same document row used by deletion. Database guards reject owner/key/version changes, resurrection and deletion of metadata tombstones. Intake's relational guards protect retained references, including direct SQL attempts.

An upload reserves a generated key and exact expected SHA-256/size before any storage call. Reservations are idempotent for actor, parent, key and input; different input conflicts. The centralized initial policy permits PDF/DOCX up to 10 MiB, two incomplete uploads per customer, 1 GiB of nondeleted reserved bytes and at most 1,000 nondeleted documents. A customer quota row serializes reservations. Filenames become bounded display names with path components, controls and Unicode formatting characters removed.

`StoreUpload` refuses to run inside a database transaction. It streams into bounded private temporary storage, checks byte count/checksum/MIME/signature, then performs a conditional immutable object write. Finalization occurs only after the application rechecks current identity, parent workflow, draft slot and precondition. It records exact object version and scan intent atomically. Failed finalization leaves Uploading metadata and private bytes; a freshly authorized identical upload may retry during the ten-minute reservation. Reconciliation never converts storage presence into authorization.

The lifecycle is Uploading → Quarantined → Available or Rejected. Technical inspection failure remains Quarantined. Quarantined and Available documents may be snapshotted into immutable revisions; Uploading documents cannot. Unreferenced documents may enter Deleting and become Deleted after exact-version deletion succeeds. Retained attachments prohibit physical deletion. An abandoned upload's late object is separately reconciled after a 24-hour grace period.

Durable kinds `documents.scan`, `documents.delete` and `documents.delete_orphan` use identifier-only Redis transport on the documents connection/queue. Jobs have a 120-second timeout, 150-second PostgreSQL lease, 180-second Redis retry interval and three attempts with 30/120-second backoff plus jitter. External storage/scanner/parser calls run outside database transactions. A scan result becomes Available only when its operation fence, Quarantined state, immutable object version and checksum still match. Expired workers cannot revive deleted documents. Deletion repeats safely against an absent exact version.

After exhausted scan attempts, an authorized explicit retry creates another logical operation; each document permits at most two such retries. Exhausted deletion operations retain their tombstones. The explicit operator command `documents:retry-deletions --limit=20` rechecks failure, references and grace under locks, records an audit event and creates an operation keyed by the prior failed operation. Scheduled reconciliation never resets attempt budgets.

`documents:reconcile --limit=20` processes bounded metadata and object pages. Persistent independent cursors prevent retained rows from starving cleanup. Unknown object versions get a durable orphan ledger before deletion; planning and execution both recheck references and the 24-hour object-age grace. A malformed object cannot block later pages. Intake's coordinated expiry action can remove expired abandoned Uploading draft slots under its own guards; Documents does not mutate Intake tables.

Downloads use an internal grant bound to actor, document version, exact object identity and a 60-second deadline. Authorization issuance and download start have separate audit events. The application opens a verified private stream outside a transaction, then revalidates identity/parent/attachment authorization and consumes the original grant before releasing bytes. This does not claim successful client receipt. Storage identities and scanner internals never appear in public metadata.

Domain tests inject storage and scanner faults to exercise rollback, duplicate delivery, fencing, retry budgets, quota/attachment contention and cleanup. Separate adapter tests and production smoke use actual private object storage and malware scanning. Parser/scanner implementation and deployment restrictions are documented with B4 integration evidence.
