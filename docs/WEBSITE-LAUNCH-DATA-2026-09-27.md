## الفحوص المنفذة الآن

1. قراءة جدول التصنيفات من المرفق ومقارنته بالقائمة المستخرجة من مصدر الموقع: تطابق 12/49 اسمًا وعلاقة وترتيبًا.
2. تحقق تفرد مفاتيح الآباء ومفاتيح الفروع تحت كل أب؛ لا تكرارات داخل النطاق.
3. تطبيق `TaxonomyChanges` الحالي في صورة PHP/Composer المثبتة: نجح التحقق من جميع الأسماء والمفاتيح وحالة النشاط وترتيب السجلات الـ61. لا كود منتج جديد ولا كتابة في قاعدة البيانات.
4. قراءة PostgreSQL بمعاملة `READ ONLY`: توجد 53 فئة إجمالًا، منها 16 نشطة؛ جميع النشطة تطابق اسم ومفتاح بيانات B8 التجريبية. لا تعارض بين مفاتيح القائمة الجديدة وأي فئة موجودة، حتى المعطلة.
5. النتيجة المتوقعة بعد اعتماد الإدخال: إنشاء 12 رئيسيًا و49 فرعيًا. إعادة التشغيل يجب أن تتعرف إلى المفاتيح نفسها دون إنشاء نسخ.
6. العقد ونسخة الموقع لم يتغيرا: OpenAPI `1.1.0-g1`، 172 عملية، SHA-256 `ae8d0a904a0042b80f9adc1224dedf8677794e2d49ca5cdf41daeb5278780be8`.

هذه فحوص إعداد بيانات، وليست إثبات تنفيذ الإدخال أو اختبارات إرسال/متصفح جديدة. لم تُعد بوابات PHPUnit/PHPStan/Pint/Composer لأن شفرة التطبيق لم تتغير. فحص بيانات الإدخال استعمل المدقق الموجود بالفعل.

## مراجعة سجلات الاختبار وحفظ التاريخ

التصنيفات النشطة الـ16 مرتبطة بـ16,000 صف مسودة و11,450 صف مراجعة. الأسماء والمفاتيح تطابق إنشاء `scripts/performance-fixture.php`، لكن لا يجوز تحويل هذه الصفوف إلى تصنيفات حقيقية بإعادة التسمية أو إعادة توجيه العلاقات.

فحص هوية أصحاب الطلبات وجد أن جميع أصحاب هذه الارتباطات يستخدمون عناوين `example.test`، دون هوية مفقودة. مع ذلك، 61 مسودة و82 مراجعة لا تطابق هوية مالك B8 بحسب نمط اسم الحساب المتوقع؛ هذه علامة تتطلب تتبعًا إلى بيانات الاختبارات قبل تحديد قائمة التعطيل النهائية، وليست إثباتًا لوجود بيانات إنتاج أو ترخيصًا بتعديلها. لم تُضمَّن عناوين أصحاب الطلبات أو محتوياتهم في التقرير.

خطة التعطيل منفصلة عن إنشاء القائمة: مراجعة كل معرف محدد وارتباطاته، ثم ضبط `active=false` عبر مالك Categories والتدقيق وحارس الإصدار، دون حذف أو تغيير اسم/slug أو UUID أو request revisions. لا يُستخدم حذف شامل أو شرط الاسم وحده لتنفيذ ذلك. السحب يمنع الاختيار الجديد وإرسال/تعديل مسودة تعتمد على فئة معطلة؛ لذلك تُراجع المسودات المرتبطة قبل تطبيقه. لا تُخفى مراجعات الطلبات القديمة أو تُعدّل لتمرير فحص جديد.

## خطة الإدخال القابلة لإعادة التشغيل بعد الاعتماد

- الاعتماد يخص `intake-launch-v1` وبصمة ملفه وقت التنفيذ. تُعاد قراءة الواقع قبل الكتابة ويُحفظ تقرير قبل/بعد. ملف JSON إعداد بيانات، وليس أداة استيراد منفذة.
- استخدام مسار إدارة Categories الحالي بصلاحية `taxonomy.manage` وجلسة موظف مكتملة، أو أداة تشغيل معتمدة تستدعي المالك نفسه وتحافظ على إعادة التفويض والتدقيق. لا إدخال مباشر يتجاوز Actions أو تصنيع `TaxonomyActor(canManage=true)` لتجاوز جلسة حقيقية.
- قراءة كل الصفحات الإدارية، بما فيها السجلات غير النشطة، ثم المطابقة بـslug للأب وبـslug داخل الأب للفرع؛ لا مطابقة بالاسم وحده.
- الموجود المطابق تمامًا يُسجّل كـno-op. الموجود بالاسم/الحالة/الترتيب المختلف يُعامل كتعارض يحتاج مراجعة؛ لا يعاد تفعيله أو تحديثه صامتًا. المفقود فقط يُنشأ، ويؤخذ معرف الأب من رد الخادم لربط فروعه.
- واجهة إنشاء التصنيفات الحالية لا تعد بـIdempotency-Key؛ لا نغيّر العقد للادعاء بذلك. القيد الفريد للـslug يمنع نسخًا مكررة. بعد رد ضائع أو سباق، تعاد القراءة والمقارنة قبل أي إعادة؛ لا slug عشوائي جديد لحل التعارض. إذا توقف الإدخال في منتصفه، يتابع من السجلات المفقودة مع الاحتفاظ بما أنشئ، دون حذف rollback يدوي.
- بعد اكتمال القائمة، يُراجع تعطيل بيانات الاختبار في إجراء محدد؛ لا تبدأ الواجهة باستعمال قائمة ثابتة كبديل عند فشل API.
- تحقق القبول: كل 12 أبًا و49 فرعًا عبر API، الترتيب والنشاط الصحيحان، ثبات IDs بعد إعادة التشغيل، عدم زيادة العدد، رفض إرسال طفل تابع لأب آخر عبر حساب/طلب اصطناعي مصرح، وسلامة التصنيفات والمراجعات التاريخية. يبقى اختبار قاعدة PostgreSQL والتزامن والجلسة الموروث لازمًا إذا أضيفت أداة تنفيذ إلى المنتج.
