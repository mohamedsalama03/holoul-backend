## 1. القرار المقترح وحدود الدفعة

إضافة وحدتين مالكتين للكتابة إلى modular monolith الحالي: `PublicPortfolio` للمحتوى والصور المعدة للنشر، و`Contact` لرسائل التواصل. يوثَّق اعتمادهما بملحق معماري إلى B0 قبل migrations. تستخدمان Audit والعقود التقنية للتخزين/المعالجة والإشعار، ولا تكتبان إلى Identity أو Projects أو Documents. يبقى PostgreSQL مصدر الحقيقة والعمل الدائم، وRedis ناقل معرفات ومحدد معدل.

المعرض ليس إسقاطًا تلقائيًا للمشاريع الخاصة، وليس إعادة استخدام لوثائق العملاء. ينشأ المحتوى التحريري مستقلًا ويُنشر بفعل موظف مخوّل. رسائل التواصل مستقلة عن طلبات الأفكار؛ لا تخلق عميلًا أو مشروعًا ولا تسجّل المرسل في النظام.

يتضمن النطاق عمليات إدارة خادمية كافية ليصبح Laravel مصدر الكتابة الوحيد، ونقلًا متحققًا من المصدر الحالي. بناء/تعديل واجهة Dashboard أو الموقع خارج هذه الدفعة. تُترك الإحصاءات الثابتة وAI المعطّل كما هما؛ لا يشمل النطاق CMS لـAbout/Services، أو محادثة، أو استعادة Claim بعد إغلاق التبويب.

إصدار API المقترح بعد النجاح: `1.4.0-public-services-candidate` مع OpenAPI 3.1.1؛ هذا اسم إصدار مقترح وليس إصدارًا منشورًا. خط الأساس هو `1.3.0-directory-sort-candidate`، 182 عملية و221 مخططًا، ببصمة `fafbc8b62976788dae0cc98492add8bed014228ad42844d2c7498ca57d1a7f4e`. تُحفظ تعريفات العمليات القائمة ومكوناتها؛ الإضافة المقترحة 20 عملية منفصلة (5 عامة و15 إدارية)، فيكون الإجمالي المتوقع بعد تنفيذها 202 عملية؛ العقد الحالي ما زال 182. يُلغى اقتراح توسيع enums/حدود capabilities المشتركة الوارد في المسودة القديمة. تُقرأ قدرات الوحدتين عبر عملية إدارية جديدة مستقلة، حتى لا تنكسر عمليات الموقع الـ31 أو مستهلكو Identity/Staff الحاليون. يجب إثبات ثبات العمليات الـ182 والمكونات القديمة آليًا قبل وصف الإضافة بأنها متوافقة. لا بصمة جديدة حتى تُجمّد النسخة المنفذة وتُختبر؛ تُسجل البصمتان وoperation/schema diff حينها، ولا يُنسخ العقد إلى الواجهة تلقائيًا.

تكون الحدود حدود Unicode code points بعد NFC وإزالة الفراغات الطرفية؛ تُقبل العربية، وتُرفض محارف التحكم وHTML بوصفه تنسيقًا فعالًا. العرض يعامل النص كبيانات ولا يستخدم HTML غير موثوق. تصنيفات المعرض منفصلة صراحة عن taxonomy UUID المستخدمة في G1.

معاملات القائمة: `category` اختياري من الرموز الخمسة؛ `limit` افتراضي 12 وبحد أقصى 48؛ `cursor` اختياري حتى 512 حرفًا. ترتيب ثابت `published_at DESC, id DESC`، مع cursor موقّع مرتبط بالفلتر والترتيب، دون offset غير محدود. تغير المنشورات بين الصفحات ليس snapshot تعاقديًا؛ يجب منع تكرار العنصر الناشئ عن ترتيب غير ثابت، والواجهة تزيل التكرار حسب id عند إعادة التحميل. لا pagination token يعطي صلاحية قراءة مسودة.

القائمة تبدأ من قيد النشر في الاستعلام. التفاصيل والصورة تتحققان من نفس قيد النشر، ولا يُكتفى بإخفاء البطاقة. العدادات تخص المنشور فقط وتُحسب باستعلام محدود/إسقاط متجدد عند النشر، دون تحميل كل المحتوى إلى Next.js. التحقق بخطط استعلام وفهارس على القيد والترتيب بعد تحديد schema النهائي.

## 4. الصور والنشر والكاش ونقل البيانات

- استيعاب صور الموظف فقط: JPG/PNG/WebP ثابتة، حتى 5 MiB للصورة و24 مليون بكسل و8 صور للمشروع كحدود مقترحة. تحقق من محتوى البايتات والحجم والبصمة والترويسة الفعلية، ورفض SVG/animation/ملف متنكر. حصص الحجز قبل المعالجة وتحديد ذاكرة/وقت/تزامن العامل، وتنظيف الحجز المنتهي.
- تخزين مدخلات المعالجة خاص؛ لا URL عام للأصل. معالجة مرة واحدة عبر منفذ تقني معزول ومثبت الإصدار: تصحيح الاتجاه وإزالة metadata، وإخراج WebP للبطاقة حتى 640px وللمعرض داخل 1800×1400 دون تكبير. AVIF مؤجل حتى دعم العامل وقياس CPU؛ ليس شرطًا للإطلاق. لا إضافة مكتبة جديدة إلى البيئة قبل اعتماد هذه الدفعة.
- لا يسمح بالنشر قبل Ready لجميع الصور اللازمة، ووجود غلاف وصورة مميزة ونص بديل، واعتماد الموظف حق نشر المحتوى. عمليات العامل تحمل IDs فقط، وتُراجع حالة المورد قبل تسجيل نتيجة متأخرة.
- كل تعديل لمحتوى منشور ينشئ نسخة تحريرية جديدة؛ النسخة العامة ثابتة إلى أن يُعاد النشر. نشر/إلغاء نشر داخل معاملة مع audit وintent لإبطال الكاش. العامل لا يعيد نشر مشروع أُلغي نشره أثناء المعالجة.
- اقتراح الكاش الأول: metadata والصور `public, max-age=0, s-maxage=60, must-revalidate`؛ ممنوع stale-while-revalidate/stale-if-error للمحتوى القابل لسحب النشر. صورة بنسخة/بصمة جديدة عند التعديل، لكن لا `immutable` سنة كاملة مع الوعد بسحبها خلال 60 ثانية. كل origin read للصورة يعيد التحقق من نشر المشروع؛ لا bucket عام يتجاوز هذا الحارس.
- إلغاء النشر يحجب الوصول الجديد في origin فورًا ويفرض purge؛ أقصى بقاء لنسخة CDN سبق جلبها 60 ثانية عند انطباق السياسة. إذا طُلب سحب فوري من جميع طبقات الكاش، تتغير السياسة إلى revalidation دائم/عدم التخزين ويعاد قياس الأداء قبل الاعتماد. لا يمكن سحب نسخة نزّلها زائر بالفعل.
- أخطاء 404/403 وعمليات الكتابة `no-store`. GET العام لا يغيّر المحتوى حسب Cookie ولا يستعمل Vary: Cookie؛ سياسة ضغط الوكيل تراجع Vary: Accept-Encoding. لا نمزج كاش الحسابات/CSRF مع العام. 304 غير مطلوب في النسخة الأولى؛ إذا أضيف لاحقًا يوثّق ويختبر مع عميل الموقع.
- ingress الحالي يفرض `no-store` لردود API ويخفي Cache-Control من FastCGI؛ لذلك تنفيذ الكاش يحتاج استثناءً ضيقًا للمسارات العامة الجديدة فقط واختبارات عدم تأثر G1/Identity. مجرد ضبط رأس من Laravel لا يكفي.

### 4.1 هوية الصورة المنشورة وحد سحب الكاش

اختيار التصميم في هذه المراجعة: `{image}` في العملية العامة هو **معرف نسخة صورة منشورة UUIDv7**، وليس معرف أصل الرفع الإداري. ينشئ كل نشر نسخة نشر مستقلة ومعرفات صور عامة جديدة لجميع صورها، حتى لو أعيد استعمال البايتات المعالجة نفسها. `PublicPortfolioImage.id` و`featured_image_id` يشيران إلى هذه النسخ العامة. معرف أصل الرفع الإداري ثابت ومستقل؛ توثق مخططاته العلاقة دون كشف مفاتيح التخزين للعامة.

كل زوج `(public_image_id, variant)` يحدد بايتات ثابتة ومجموعة نشر واحدة. يمنع استبدال محتوى هذا الزوج أو إعادة استخدام معرفه. تغيير البايتات أو إعدادات المعالجة، أو إعادة النشر بعد السحب، يصدر روابط جديدة. لا تعديل لمسار العملية ولا عملية إضافية. يجوز تخزين البايتات المتطابقة مرة داخليًا، لكن يبقى التفويض لكل نسخة نشر على حدة.

عند استبدال النسخة المنشورة أو سحب المشروع، تمنع قراءات origin الجديدة جميع معرفات صور النسخة السابقة فور commit، وتعيد 404/no-store. إعادة نشر المشروع لاحقًا لا تحيي الروابط المسحوبة. aliases الخاصة بمشاريع UUIDv4 تبقى لروابط تفاصيل المشاريع؛ ربط معرفات صور المصدر القديم بالأصول المستوردة خريطة نقل داخلية، ولا يحوّل معرف صورة منشورة قديمة إلى بايتات جديدة.

نافذة 60 ثانية تُقاس من commit السحب إلى آخر استجابة مخبأة مسموحة للطلبات الجديدة عبر **المسار الكامل**؛ ليست 60 ثانية لكل طبقة. الحل الأول المقترح طبقة shared cache واحدة للمسارات العامة، مع revalidation للمتصفح ومنع مخازن Next.js/HTML/الصور الوسيطة من إضافة مدة مستقلة. عند إضافة طبقة أخرى يجب أن تحافظ على Date/Age ومدة الصلاحية المتبقية، أو تُعطّل حتى تثبت الاختبارات الميزانية الإجمالية. لا stale-while-revalidate ولا stale-if-error ولا خدمة نسخة قديمة عند تعطل origin.

الموقع الحالي يستعمل `/api/portfolio-images/{id}` الذي يعيد رأسًا مستقلًا `public, max-age=60, must-revalidate` ويجلب صور Dashboard عبر `cache: no-store`. وجود 60 هنا وحده لا يثبت حد 60 ثانية بعد إضافة cache آخر. استبدال الموصل أو تعديل هذه السياسة مسؤولية فريق الموقع عند الربط؛ لا يُعلن نجاح شرط السحب للموقع الحالي من اختبار Laravel وحده. إعداد Nginx وCDN إن استُخدم ضمن اختبار مسار النشر الفعلي، ولا نفترض وجود CDN مُهيأ الآن.

مصفوفة القبول: تسخين القائمة والتفاصيل والتصنيفات والعدادات وصور card/gallery لنسخة A؛ نشر B والتحقق أن صور A محجوبة في origin؛ سحب B وتسجيل وقت commit؛ قراءة كل مورد من origin ومن أصل الموقع والمتصفح والوكيل وأي CDN حتى تجاوز 60 ثانية؛ التحقق من اختفاء العنصر وانخفاض العدادات و404 للصور/التفاصيل دون fallback. تشمل الاختبارات origin غير المتاح، انتهاء التخزين المتزامن، إعادة نشر C، ومهمة معالجة متأخرة؛ لا ترجع روابط A/B بعد C. تحفظ Date/Age/Cache-Control ونتائج التوقيت. النسخ التي نُزّلت بالفعل أو تبويب يعرض ذاكرة قديمة لا يمكن سحب بايتاتها عن بُعد؛ حد القبول يخص الوصول الجديد والتحديث من الشبكة.

المصدر الحالي وفق فحص الشفرة: Dashboard يخزن `projects.json` والصور WebP في `PORTFOLIO_DATA_DIR`، افتراضيًا `.data/portfolio`، ويولد UUIDv4. لا تُنسخ مفاتيح الوصول أو جلسة `holoul_portfolio_session` إلى Laravel؛ تستبدل إدارة المصدر بـIdentity/MFA والصلاحيات المعتادة.

خطة النقل: جرد read-only للمعرفات والمرجعيات والملفات والبصمات وحالة النشر، ثم export متسق بعد وقف كتابات المعرض، فاستيراد جاف يتحقق من الحدود وحقوق النشر، ثم استيراد قابل لإعادة التشغيل بمفتاح مصدر فريد. المعرف الداخلي الجديد UUIDv7؛ جدول alias فريد يحفظ UUIDv4 القديمة، وواجهات القراءة تقبل alias لتبقى الروابط القديمة صالحة. `id` المعروض للسجل المستورد يظل legacy UUIDv4، وللسجل الجديد UUIDv7. هذا استثناء موثق للحفاظ على روابط موجودة، لا تغيير لقاعدة IDs في المجالات الأخرى. لا slug جديد.

تُراجع أي مادة موجودة تتجاوز الحدود بدل إسقاطها صامتًا. تقارن أعداد المنشور/المسودة وكل صورة وبصمتها؛ لا يُحذف المصدر القديم حتى قبول النقل وفترة رجوع معتمدة. عند التحويل تُوقف كتابة المخزن القديم وتستهلك واجهة اللوحة Laravel، فلا يبقى مصدران يختلفان. المسودات لا تنشر تلقائيًا لمجرد أنها مستوردة.

## 5. إنشاء رسالة التواصل

`PublicContactInput` حقول مسموحة فقط:

| الحقل | القاعدة المقترحة |
|---|---|
| `full_name` | مطلوب، 2–120 حرفًا، Unicode NFC وفراغات مطبعة |
| `email` | مطلوب، حتى 254، نفس تطبيع Identity دون استدلال على وجود حساب |
| `phone` | مطلوب دولي يبدأ +، تحقق libphonenumber إلى E.164؛ لا تخمين بلد |
| `company` | اختياري null أو نص 1–160؛ النص الفارغ يصبح null |
| `message` | مطلوب 10–5,000؛ نص عادي متعدد الأسطر، تطبيع نهايات الأسطر دون إعادة كتابة المعنى |

النموذج لا يقبل مرفقًا أو user_id أو customer_id أو status أو عنوان مستلم الإشعار. جسم JSON لا يتجاوز 32 KiB؛ UTF-8 وتعداد الحقول محدودان. لا يطلب إدخال بيانات حساب موجود أو تأكيد بريده لترك رسالة.

`Idempotency-Key` مطلوب، UUID عشوائي. معاملة PostgreSQL تضمن تفرد HMAC(scope للعملية + key)، وتقارن بصمة الجسم المطبع. التخزين يتضمن receipt ثابتًا ووقت انتهاء 72 ساعة من أول حفظ. إعادة الطلب المطابق داخل المدة تعيد نفس 201 والـreceipt والجسم، ولو دارت جلسة المستخدم؛ CSRF الجديد يظل مطلوبًا. جسم مختلف بالمفتاح نفسه يعيد 409. طلبان متزامنان بالمفتاح نفسه ينتجان صفًا واحدًا وintent إشعار واحدًا. لا تُعاد الرسالة أو بيانات المرسل ضمن receipt، فلا يتحول المفتاح إلى رابط قراءة PII.

بعد انتهاء نافذة 72 ساعة لا يُسمح للواجهة بإعادة إرسال تلقائية؛ يُعامل الإرسال اللاحق كتواصل جديد. توثّق سياسة حذف سجلات idempotency وتعارض المفتاح عند تنفيذها، وتختبر حدود الوقت قبل تجميد OpenAPI. لا نَعِد بمنع تكرار أبدي بمفتاح منتهي أو بمفتاح جديد.

الرد المقترح `PublicContactReceipt`: `id` UUIDv7، `reference` مثل CNT-2026-00001 من sequence، `status=received`، `received_at` UTC. نجاح 201 يعني رسالة محفوظة وإشعارًا مسجلًا كعمل دائم، لا أن SMTP سلّمها الآن. فشل PostgreSQL أو تسجيل intent يلغي المعاملة ويعيد 503/500 آمنًا، ولا يصدر receipt وهمي.

الإشعار بعد commit عبر durable operation؛ يحمل معرف الرسالة فقط. الرسالة البريدية للموظف لا تحتوي كامل PII/النص. تحتوي مرجعًا؛ يضاف رابط قراءة فقط بعد جاهزية صفحة موظف مخوّل واجتياز بوابة الربط أدناه. لا يُرسل autoresponder عام إلى كل بريد يدخله مجهول لتجنب الإساءة. SMTP لا يضمن exactly-once بعد نتيجة غامضة؛ تسجل `delivery_uncertain` للمراجعة دون إعادة إرسال عمياء. الفشل المؤكد يعاد وفق retry محدود وbackoff، ولا تضاعف المحاولة سجل التواصل. المصدر الدائم يبقى قابلًا للقراءة للموظف ولو تعطل البريد.

### 5.1 ربط صفحة قراءة الرسائل قبل التشغيل

مسار صفحة Dashboard المقترح للتنسيق: `/admin/contact-messages/{message}`، ويستهلك `adminContactDetail` عبر `/api/v1/admin/contact-messages/{message}`. الأول مسار واجهة وليس API جديدة ولا صفحة موجودة نضمنها الآن. فريق Dashboard يبني الصفحة وربطها؛ Backend يسلم العقد والبيانات الاصطناعية ومصفوفة الصلاحيات ويعيد فحص الإذن خادميًا في كل قراءة.

تتطلب الصفحة دخول موظف مكتمل MFA وصلاحية `contact.read`، وتعرض بيانات الاتصال والنص للرد بواسطة الموظف. لا إرسال رد نيابة عنه ولا API دردشة ضمن هذه الدفعة. `info@holoul.ly` عنوان استقبال فقط؛ لا ينشئ حسابًا ولا يمنح صلاحية. لا قراءة عامة بديلة برقم الإيصال أو البريد أو رابط البريد.

يمكن تطوير الحفظ والإيصالات والإشعار واختبارها في Mailpit قبل جاهزية الصفحة؛ قالب الاختبار في هذه الحالة يحتوي مرجعًا فقط دون رابط ميت. توليد رابط قراءة وتفعيل إشعارات الإنتاج يظلان معطلين حتى يعتمد الفريقان مسار الصفحة، وتثبت رحلة موظف مخوّل ناجحة، ويُرفض الموظف غير المخوّل/غير المكتمل MFA. لا يكفي رد HTTP 200 لصفحة تسجيل دخول. الرابط يستخدم أصلًا تشغيليًا معتمدًا ولا يحمل token عامًا أو PII؛ يجتاز توليده اختبار المسار والإذن قبل تفعيله.

### 5.2 تطابق نموذج الواجهة وحد إعادة المحاولة

عند الربط تحول الواجهة `name` إلى `full_name`، وتجمع كود الاتصال والرقم في قيمة `phone` دولية صريحة؛ لا ترسل حقل `country` أو العلم. تُثبت حدود Unicode والتطبيع وخرائط أخطاء الحقول في العقد الجديد دون توسيع مخططات مشتركة قديمة. نجاح 201 يعرض «استُلمت الرسالة»، لا «وصل البريد».

نافذة الضمان نصف مفتوحة: من وقت قبول وحفظ العملية الأول `t0` وحتى ما قبل `t0 + 72h`. داخلها يعيد المفتاح والجسم المطبع المتطابقان الإيصال نفسه؛ الجسم المختلف 409. عند بلوغ الحد تنتهي إعادة النتيجة القديمة، وأي إرسال لاحق يُعامل كعملية جديدة خارج ضمان منع التكرار، ولو استُعمل المفتاح القديم؛ يجب أن تُحدد مفاتيح التخزين المنتهية وتُستبدل ذريًا، لا أن يتوقف السلوك على توقيت عامل تنظيف. يعاد التحقق من الوقت بعد الحصول على قفل التنافس، ويحدد العقد النهائي نقطة `t0` ووقت الخادم. تختبر حدود قبل الانتهاء وعنده وبعده مع تنافس حقيقي.

الواجهة تحفظ المفتاح والجسم للطلب نفسه، وتوقف الإعادة الآلية عند انتهاء النافذة أو عندما لا تعرف هل حُفظت الرسالة خارجها. لا تولّد مفتاحًا جديدًا تلقائيًا لنتيجة غير محسومة. إعادة إرسال مقصودة لاحقًا قرار واضح من المستخدم؛ الإيصال القديم والمصدر الدائم لا يُحذفان بانتهاء مفتاح منع التكرار.

حدود مقترحة: 5 رسائل/ساعة لكل IP، و3/ساعة لكل HMAC بريد، و100/ساعة للبيئة كحد تشغيل أولي، وجسم 32 KiB. تعاد 429 مع Retry-After عند الاستنفاد، و503 عند تعذر حارس المعدل؛ لا captcha افتراضيًا ولا تعطيل لحماية Origin. المعدل يحسب بنفس الطريقة للبريد الموجود وغير الموجود؛ لا يجرى بحث حساب أصلًا. يُعاد تقييم الأرقام بحمل واقعي وشبكات NAT قبل الإطلاق.

## 6. الإدارة والصلاحيات والخصوصية

عمليات Backend الإدارية التالية جزء من الاقتراح لأنها لازمة لمصدر واحد ومتابعة التواصل؛ واجهة Dashboard ليست جزء التنفيذ هنا. أسماؤها النهائية تدخل مراجعة العقد قبل تفعيلها:

| المجموعة | المسارات/الأفعال المقترحة |
|---|---|
| قراءة المعرض للموظف | GET `/api/v1/admin/portfolio/projects` و`/{project}`؛ صفحات محدودة وفلاتر حالة |
| تحرير المعرض | POST `/api/v1/admin/portfolio/projects`، PATCH `/{project}` مع If-Match |
| إدخال صورة | POST `/{project}/images` للحجز ثم PUT `/{project}/images/{image}/content` لبايتات خام، GET حالة محددة؛ مع فحص الإذن عند الحجز والكتابة والإنهاء |
| حذف صورة تحريرية | DELETE `/{project}/images/{image}` مع If-Match؛ لا حذف صورة يستعملها إصدار منشور دون نشر تعديل/سحب الإصدار |
| النشر والسحب | POST `/{project}/publications` وPOST `/{project}/unpublications` مع If-Match ومفتاح منع تكرار؛ تحقق إضافي وحديث للصلاحية |
| رسائل التواصل | GET `/api/v1/admin/contact-messages` و`/{message}`؛ PATCH الحالة مع If-Match؛ DELETE محتوى الرسالة عبر عملية redact مدققة لا حذف audit |

صلاحيات جديدة مقترحة: `portfolio.read`, `portfolio.manage`, `portfolio.publish`, `contact.read`, `contact.manage`, `contact.redact`. الاقتراح الأول يمنحها لـSuper Admin وAdministrator فقط ويترك بقية الأدوار دون توسعة. النشر والسحب والحذف الحساس تتطلب بريدًا مؤكدًا وMFA وتأكيد كلمة مرور حديثًا؛ عنوان الإشعار المحدد من صاحب المشروع هو `info@holoul.ly`؛ مستخدمو النظام المخولون بقراءة الرسائل يحتاجون تعيينًا مستقلًا ولا يُستنتجون من العنوان. لا تضاف قيم إلى `IdentityCurrentUser.capabilities` (35 قيمة) أو `StaffCapabilitiesResponse` (37 قيمة)، ولا تتغير `confirmable_capabilities` أو حدودها. مورد جديد `GET /api/v1/admin/public-content/capabilities` يعرض فقط صلاحيات الموظف الحالي للوحدتين، كحقول boolean ثابتة `portfolio_read`, `portfolio_manage`, `portfolio_publish`, `contact_read`, `contact_manage`, `contact_redact`، مع `recent_password_confirmation` وفق الجلسة. المورد للموظف المكتمل MFA، وبياناته private/no-store؛ ليس سلطة بديلة عن تفويض كل عملية. تستعمل الأفعال الحساسة آلية `identityConfirmPassword` القائمة دون تغيير مدخلها أو ردها. لا يتغير تفويض دعوات الموظفين: Super Admin حسب السياسة القائمة، وAdministrator لدعوة Support فقط. كل ذلك يحتاج اعتمادًا لأنه يغير كتالوج الصلاحيات، ولا يمنح لقب الدور تجاوزًا عامًا لسياسات الموارد.

مدة الاحتفاظ 180 يومًا **معلّقة**؛ لا تعدها هذه المراجعة سياسة معتمدة، وتظل جدولة التنقيح الآلي معطلة. لا يؤخر ذلك تطوير الحفظ والإيصالات والإشعارات ومسار التنقيح اليدوي المخوّل والمدقق. قبل قبول سياسة الاحتفاظ للإطلاق يلزم قرار المالك بالمدة والاستثناءات وأثر النسخ الاحتياطية؛ وقبل تشغيل أي تنقيح دوري يلزم اعتماد منفصل لهذه السياسة. يحتفظ audit بالمعرفات ونوع الفعل فقط دون محتوى الرسالة. طلب الخصوصية يُتحقق منه عبر إجراء موظف، ولا يتاح مسار حذف مجهول بالبريد. التخزين والنسخ مشفرة؛ توثق مدة بقاء البيانات في النسخ الاحتياطية وطريقة إعادة تطبيق أوامر التنقيح بعد الاستعادة. المدة اقتراح تشغيلي وليست تفسيرًا قانونيًا أو سياسة معتمدة.

## 8. بوابات القبول المطلوبة بعد الاعتماد

- مقارنة 182 عملية قديمة وكل مخطط مشترك قبل/بعد؛ لا تغيير طلبات أو أكواد أو رؤوس G1/Admin القائمة. توثيق schemas والإضافات الجديدة والبصمتين، وفحص route/spec drift وresponse samples.
- fresh migrations + upgrade من مرشح C1/Staff الحالي ذي 31 migration ببيانات اصطناعية تمثل التاريخ، وإثبات بقاء immutable revisions وملكية العملاء وصلاحيات runtime. لا reset للقاعدة الحية.
- المعرض: عدم كشف draft أو صورها بالـID، تبديل/سحب أثناء تحميل صورة أو إتمام عامل، cursor وفلاتر وعدادات وحدود، تنافس نشر وتعديل، منع source URL/PII، كاش وهوية مستقلة، قياس حداثة سحب النشر من origin والكاش.
- التواصل: عميل/مجهول بنفس البروتوكول، CSRF/Origin/429، تطبيع العربية والهاتف، تنافس مفتاح متطابق/مختلف، rollback عند فشل audit/intent، تعطل البريد والنتيجة الغامضة والـretry، وصول الموظف والتدقيق والتنقيح دون كشف الرسائل.
- وراثة جميع اختبارات SessionLifecycle وGuestSessionIsolation وPostgreSQL concurrency. اختبار قراءة/كتابة عامة بجانب جلسة مصادق عليها، طلب مصادق قديم، login/MFA/logout المتزامنة، وclaim أثناء الدوران. لا تبديل/إحياء جلسة من GET عام أو contact response متأخر.
- PHPUnit وArchitecture وPHPStan/Larastan level 10 وPint وComposer validate/audit وDocker build/runtime وفحوص parser الجديدة؛ لا إعادة تعريف الاختبارات لإخفاء إخفاق.
- رحلة متصفح حقيقية للموقع ولوحة المدير بعد الربط بواسطة مالك الواجهة، ثم قياس VPS والاستعادة؛ النجاح المحلي لا يغلق B8.

## 9. ما يُعتمد الآن وما يبقى معلّقًا

المطلوب اعتماد نطاق الوحدتين والعمليات العامة والإدارة الخادمية، ودعم IDs المعرض القديمة، وسياسة سحب الصور خلال 60 ثانية، ومنح الصلاحيات المقترحة. تطوير التواصل لا ينتظر تحديد مدة 180 يومًا. تفعيل إشعارات الإنتاج يحتاج إعداد الإرسال إلى `info@holoul.ly` وجاهزية صفحة Dashboard المخوّلة؛ قبول سياسة الاحتفاظ للإطلاق يحتاج قرارًا بالمدة والاستثناءات، والتنقيح الآلي معطل حتى اعتماده. قبل نقل المحتوى يلزم جرد وحقوق نشر. دومين الإنتاج المحدد هو `holoul.com.ly`؛ قبل الإنتاج يلزم Staging ومزود البريد وDNS/TLS ومسؤول التشغيل وRPO/RTO. `staging.holoul.com.ly` اقتراح فقط.

بعد الاعتماد يبدأ تنفيذ هذه الدفعة فقط في مرشح مستقل عن G1، مع ADR واختبارات وحفظ الأدلة السابقة. لا تعديل لواجهة الموقع أو Dashboard، ولا نشر إنتاجي ضمن هذه المسودة.
