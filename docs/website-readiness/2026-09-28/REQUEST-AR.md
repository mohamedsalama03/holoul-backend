# HOLOUL — متطلبات الخادم لاستكمال الموقع والأداء

**الجهة المستلمة:** فريق Backend وDevOps، بالتنسيق مع فريق الواجهة.

**تاريخ المراجعة:** 27 سبتمبر 2026؛ تحديث مقارنة مرجع API في 28 سبتمبر 2026. **نسخة الموقع المرجعية:** `39536e6` على فرع `main` في [holoul-frontend](https://github.com/mohamedsalama03/holoul-frontend).

هذا الملف يخص الموقع العام وحساب العميل وتقديم الأفكار ومتابعة الطلبات. لا يتضمن تطوير لوحة المدير المنفصلة. يوضح الوظائف الموجودة بالفعل، والنواقص، وما يجب تسليمه واختباره قبل اعتبار الموقع جاهزًا للإطلاق.

## 1. الخلاصة والأولويات

الخادم الأساسي موجود، والواجهة مربوطة بعقده. لا نحتاج إعادة بناء التسجيل أو تقديم الأفكار من الصفر. نحتاج استكمال الخدمات العامة الناقصة، والتحقق من الرحلات الموجودة، وتجهيز تشغيل إنتاجي قابل للقياس.

## 2. مرجع التكامل وحالة التحقق

- مصدر الحقيقة للربط الحالي: [عقد OpenAPI الموجود في المستودع](../contracts/holoul-api-v1.openapi.json).
- OpenAPI: **3.1.1**. إصدار API: **1.1.0-g1**. عدد العمليات الكلي: **172**. العمليات المستهلكة في الربط الحالي للموقع: **31**، مدرجة في الملحق.
- SHA-256: `ae8d0a904a0042b80f9adc1224dedf8677794e2d49ca5cdf41daeb5278780be8`.
- نجحت سابقًا 65 حالة اختبار للواجهة، وفحوص TypeScript وLint والعقد، و46 فحصًا للتوجيه والحماية عبر HTTP. هذه ليست بديلًا عن اختبار الرحلات كاملة داخل المتصفح.
- تم إصلاح التوجيه المحلي إلى `https://localhost:8443`، وأظهر اختبار المستخدم تحميل حساب العميل. لا نعيد اعتبار غياب التوجيه المحلي مشكلة قائمة.
- لم تكتمل بعد جميع اختبارات الإرسال والمستندات وClaim والأداء على بيئة إنتاجية مماثلة. لا تُعد النسخة الحالية شهادة جاهزية إنتاجية.

**أي API جديدة أدناه هي طلب تطوير، وليست عملية متاحة ضمن العقد الحالي.** على فريق الخادم اختيار المسارات و`operationId` واعتمادها في نسخة عقد جديدة مع سجل التغييرات والبصمة. لا نغيّر العمليات الحالية أو نفترض وجود حقول غير موثقة. الوثائق القديمة التي ذكرت عدم وجود ingress أو Git تصف مرحلة سابقة.

### مراجعة المرجع الذي أرسله صاحب المشروع — 28 سبتمبر 2026

تمت قراءة [مرجع API المحلي](http://localhost:8876/) وتحميل [نسخة JSON](http://localhost:8876/openapi.json)، ثم مقارنتها بالعقد المثبت في الموقع:

- النسخة المعروضة: `1.3.0-directory-sort-candidate`، بمعيار OpenAPI `3.1.1`، وعدد **182 عملية**.
- بصمة JSON: `fafbc8b62976788dae0cc98492add8bed014228ad42844d2c7498ca57d1a7f4e`، وتطابق البصمة المذكورة في دليل المرجع. نجح التحقق البنيوي من العقد.
- أضيفت **10 عمليات** تخص دعوات الموظفين ودليلهم وصلاحياتهم، وأضيف خيار ترتيب إلى `adminCustomerList`. لم تُحذف أي عملية من النسخة السابقة.
- لم تتغير تعريفات **31 عملية** يستهلكها الموقع حاليًا، ولا **71 مكوّنًا مرجعيًا** تعتمد عليه هذه العمليات بصورة مباشرة أو غير مباشرة. هذه نتيجة مقارنة للعقد، وليست اختبارًا للتنفيذ الفعلي أو للأداء.
- ما زالت APIs العامة لمعرض المشاريع ورسائل Contact والإحصاءات العامة غير معرّفة في هذا المرجع. عمليات المشاريع وتقارير المدير الخاصة لا تحل محلها؛ تبقى الطلبات الواردة في الأقسام التالية قائمة.
- الرابط المرسل يشير إلى [aiRunCancel](http://localhost:8876/#/AI/aiRunCancel). هذه العملية موجودة دون تغيير في العقدين؛ عدم ظهور زر الإلغاء حاليًا نقص في ربط الواجهة، وليس API مفقودة من الخادم.
- المنفذ `8876` يعرض وثائق فقط، وليس عنوان خادم API للتطبيق. يبقى أصل المتصفح المحلي `https://localhost:8443` وتبقى طلباته نسبية.
- لم تُستبدل نسخة العقد المثبتة أو الأنواع المولدة ضمن هذه المراجعة، ولم تُنفَّذ عمليات إلغاء أو كتابة على الخادم. المرجع يصف نسخة مرشحة للتكامل، مع بقاء اعتماد أداء الإنتاج معلقًا على الخادم المستهدف.

بيانات الدومين وبريد الاستقبال وقائمة التصنيفات الأصلية متاحة في [ملف بيانات الإطلاق](LAUNCH-DATA-AR.md).

## 3. حزمة التسليم المطلوبة من فريق الخادم

1. نسخة OpenAPI محدثة ومعتمدة لكل الإضافات، مع الإصدار والبصمة وشرح التوافق مع الإصدار الحالي.
2. عنوان Staging موحد للموقع وAPI، والدومين الإنتاجي المقترح، وشهادة HTTPS موثوقة، وتحديد مسؤول النشر.
3. ملف إعدادات نموذجي **بأسماء المتغيرات دون أسرار**، وتعليمات التشغيل والترحيل وتشغيل العمال والإيقاف والتراجع الآمن.
4. عينات طلبات وردود ناجحة وفاشلة لكل عملية جديدة، وحدود الحقول والترقيم والتخزين المؤقت وRate Limits.
5. بيانات اختبار اصطناعية: عميل مؤكد، عميل غير مؤكد، عميل ثانٍ لاختبار العزل، وتصنيفات ومشاريع معرض منشورة وغير منشورة.
6. طريقة استلام رسائل الاختبار في Staging، ومخطط روابط التأكيد والاستعادة، وسياسة البريد الإنتاجي.
7. ملفات PDF وDOCX اصطناعية آمنة، وبيانات اختبار لحالات الرفض والانتهاء والتعارض دون إضعاف الحماية.
8. مصفوفة صلاحيات مختصرة: ما يقرأه الزائر، وما يخص العميل، وما يتطلب موظفًا. لا تستخدم صلاحيات المدير لتشغيل صفحات العملاء.
9. تقرير تشغيلي عن قاعدة البيانات والتخزين والعمال والفحص والبريد وAI، وما هو مفعّل أو معطّل في كل بيئة.
10. تقرير الأداء والأخطاء وعمليات الاستعادة، مع إعدادات الخادم وحجم بيانات الاختبار وطريقة إعادة الاختبار.

لا نحتاج ملف `.env` الإنتاجي أو مفاتيح قاعدة البيانات أو SMTP أو AI داخل GitHub أو المحادثة. يضبطها فريق التشغيل في مخزن أسرار/إعدادات الخادم، وتُسلّم حسابات الاختبار بقناة آمنة.

## 4. API معرض المشاريع العامة — المطلوب الجديد

### الحالة الحالية

الواجهة تستخدم `PORTFOLIO_API_URL` على خادم Next.js للاتصال بخدمة المعرض في Dashboard المحلي. تجلب قائمة المشاريع كلها، ثم تفلترها وتستخرج صفحة التفاصيل منها. هذه الخدمة ليست Public Portfolio API ضمن عقد Laravel المعتمد، ويجب إزالة اعتماد الموقع على تشغيل واجهة لوحة المدير كي يعرض المشاريع.

### المطلوب من Backend

- قراءة قائمة **المشاريع المنشورة للعامة فقط**، مع فلتر التصنيف، وترتيب ثابت، وترقيم صفحات محدود. اقتراح البداية: 12 مشروعًا لكل صفحة وحد أقصى 48، يُعتمد في العقد.
- قراءة تفاصيل مشروع واحد مباشرة، دون تحميل المعرض كله. المعرّف الحالي في الموقع هو `id`؛ استخدام `slug` لاحقًا يتطلب توثيق التحويل والروابط القديمة.
- قراءة تصنيفات المعرض وأعداد المشاريع المنشورة تحت كل تصنيف، بما يتيح أعداد الفلاتر الصحيحة دون تنزيل كل السجلات.
- فصل تصنيفات المعرض عن تصنيفات تقديم الأفكار، أو توثيق الربط بينهما صراحة. التصنيفات الحالية للمعرض هي `web` و`mobile` و`business` و`commerce` و`custom`.
- إدارة مصدر بيانات النشر بواسطة الخادم، مع وجود مصدر واحد للإضافة والتعديل والنشر وإلغاء النشر من لوحة المدير. واجهات إدارة تلك البيانات مسؤولية مشروع اللوحة خارج هذا التكليف.

### البيانات التي تحتاجها الواجهة

الأسماء الآتية تصف الحقول المطلوبة وظيفيًا؛ تُحسم أسماؤها وأنواعها النهائية في OpenAPI:

| المورد       | البيانات المطلوبة                                                                          |
| ------------ | ------------------------------------------------------------------------------------------ |
| بطاقة مشروع  | معرف ثابت، عنوان، وصف مختصر، التصنيف، صورة الغلاف مع الأبعاد والنص البديل، تاريخ آخر تحديث |
| تفاصيل مشروع | بيانات البطاقة، وصف كامل كنص آمن، معرض صور مرتب، صورة مميزة                                |
| صورة عامة    | معرف أو رابط معتمد، `width` و`height` و`alt`، نوع الوسائط، نسخ مناسبة للبطاقة والمعرض      |
| صفحة نتائج   | العناصر، cursor التالي أو آلية ترقيم موثقة، ومعلومات الفلاتر اللازمة                       |
| تصنيف        | معرف ثابت واسم عرض وترتيب وعدد المشاريع المنشورة                                           |

**شروط القبول:** لا تُكشف المسودات أو مشروعات العملاء الخاصة أو ملفاتهم. المشروع غير المنشور لا يكون متاحًا بمجرد معرفة معرفه. تُختبر الصور مباشرة، وليس إخفاء البطاقة فقط. لا تُستخدم `/api/v1/projects` الخاصة بالعميل كمعرض عام.

تُعالج صور المعرض وتُضغط مرة عند إدخالها، مع نسخ WebP/AVIF عند الدعم. تُعاد روابط قابلة للتخزين المؤقت ومحددة المصدر؛ لا ننشئ خدمة تجلب أي URL يرسله الزائر. تُوثق حدود عدد الصور وأحجامها ومصدر الصور الحالية وخطة نقلها. تُحسم آلية إبطال الكاش عند التعديل وإلغاء النشر؛ الصور العامة المعتمدة للنشر تختلف عن مستندات العملاء الخاصة.

## 5. إرسال رسائل التواصل — المطلوب الجديد

نموذج Contact الحالي يعرض صراحة أنه يحفظ محليًا فقط. المطلوب عملية عامة موثقة تقبل بيانات النموذج وتحفظها بشكل دائم قبل إرجاع نجاح حقيقي.

| بيانات النموذج | المتطلبات المقترحة المطابقة للواجهة الحالية                     |
| -------------- | --------------------------------------------------------------- |
| الاسم          | مطلوب، حتى 120 حرفًا؛ توثيق الحد الأدنى والتطبيع                |
| البريد         | مطلوب، صيغة صحيحة، حتى 254 حرفًا                                |
| الهاتف         | مطلوب؛ تحويل كود الدولة والرقم إلى رقم دولي والتحقق منه خادميًا |
| الشركة         | اختيارية، حتى 160 حرفًا                                         |
| الرسالة        | مطلوبة، حتى 5,000 حرف؛ التعامل معها كنص غير موثوق               |

- رد نجاح يتضمن مرجع استلام وحالة واضحة وفق العقد الجديد؛ قبول الطلب لا يعني ضمان وصول البريد إلى الموظف في اللحظة نفسها.
- إشعار الفريق عبر آلية موثوقة بعد حفظ الرسالة. فشل SMTP لا يفقد الرسالة ولا يولّد نسخًا مكررة عند إعادة المحاولة.
- توثيق دعم `Idempotency-Key` ومدة الاحتفاظ به وطريقة إعادة نفس الرد عند إعادة الطلب نفسه؛ يطبق العميل ذلك بعد اعتماد العقد.
- حماية CSRF وOrigin متوافقة مع المعمارية الحالية، وRate Limits موثقة و`429` مع `Retry-After`، وآلية مكافحة إساءة الاستخدام تتناسب مع الحاجة الفعلية.
- عدم كشف وجود حساب من عدمه بناءً على البريد، وعدم إرجاع محتوى داخلي أو تفاصيل قاعدة البيانات.
- تحديد الجهة المستلمة للرسائل، وصلاحيات الاطلاع، ومدة الاحتفاظ، وآلية الحذف والتعامل مع طلبات الخصوصية.

**اختبار القبول:** تظهر رسالة اصطناعية واحدة في مصدرها الدائم، ويصل إشعارها إلى صندوق الاختبار، ويعيد تكرار الإرسال المطابق نفس النتيجة وفق سياسة العقد. تعطل البريد لا يؤدي إلى نجاح وهمي أو فقد الرسالة.

## 6. إحصاءات الرئيسية — إضافة إذا أُريد تحديثها تلقائيًا

الأرقام الحالية معتمدة من صاحب الموقع داخل `src/lib/company-statistics.ts`: **734 مشروعًا، 127 عميلًا، 1950 طلب دعم منجزًا**. ليست إحصاءات حية من قاعدة البيانات، وليست حالات نجاح تجريبية.

المطلوب، إذا أُريد تحديثها دون نشر الواجهة:

- مورد عام صغير للأعداد الثلاثة، وتاريخ تحديثها، مع سياسة واضحة عند عدم توفر الرقم: قيمة غير متاحة بدل تحويلها إلى صفر مضلل.
- توثيق معنى كل عداد: المشاريع المنجزة فعلًا لا طلبات الأفكار؛ العملاء وفق تعريف أعمال موحد؛ الدعم المغلق وفق مصدر معتمد.
- تحديد كيفية احتساب السجل التاريخي السابق للنظام. إذا لم تكن سجلات الدعم موجودة، تُدار قيمة تاريخية معتمدة بدل اختراع تذاكر وهمية.
- أرقام مجمعة لا أسماء عملاء ولا سجلات خاصة، محسوبة أو مخزنة مسبقًا؛ لا ننفذ تجميعًا ثقيلًا عند كل زيارة.

يجوز إبقاء الأرقام ثابتة بقرار صاحب المشروع؛ عندها هذا الـAPI ليس شرط تشغيل لبقية الموقع.

## 7. الحسابات والبريد وملف العميل — تحقق من الموجود

عمليات التسجيل والدخول والخروج والتأكيد وإعادة الإرسال واستعادة كلمة المرور موجودة. المطلوب من الفريق إثبات عملها مع الواجهة الحالية، وتزويدنا بسياسات انتهاء الرموز والجلسات وحدود إعادة الإرسال.

- التسجيل يرسل `full_name` و`email` و`phone` وكلمة المرور وتأكيدها حسب العقد. تأكيد أن مسار التسجيل الطبيعي ينشئ ملف العميل المطلوب، وأن بياناته تظهر في `/api/v1/customers` لصاحبه فقط.
- قراءة ملفات العميل تعيد صفرًا أو ملفًا واحدًا. إذا كانت حالة الحساب دون ملف ممكنة، نحتاج إجراء إصلاح رسمي بصلاحيات صحيحة؛ تعديل الهاتف الحالي لا ينشئ ملفًا مفقودًا. لا نضيف API جديدة إذا كانت المشكلة تحل بضمانات التسجيل أو مسار إصلاح موجود.
- استمرار تحميل بيانات العميل المسجل للعرض فقط في تقديم الفكرة، واشتقاق ملكية الطلب من الخادم، دون إرسال `customer_id` أو `user_id` أو بيانات اتصال بديلة للتحايل على الملكية.
- توثيق `profile_complete_required` والتحقق من البريد، وإرجاعهما بما يسمح بإظهار الإجراء الصحيح للمستخدم.
- العمليات الإضافية مثل `identityUpdateCurrentUser` وتغيير كلمة المرور وإدارة الجلسات موجودة في العقد، لكن واجهة الحساب الحالية لا تستهلكها كلها. هذا عمل واجهة عند طلبه، وليس سببًا لاختراع APIs مكررة.

**البريد:** البيئة المحلية تستخدم Mailpit على `http://localhost:8025`؛ هذا صندوق اختبار، وليس إرسالًا إلى Gmail أو العملاء. الإنتاج يحتاج مزود إرسال فعليًا ودومين مرسلًا معتمدًا وإعداد SPF/DKIM/DMARC، وقياس وصول البريد ومتابعة الارتداد والفشل.

صفحات الواجهة الحالية تستقبل رمز التأكيد أو الاستعادة في fragment مثل `/verify-email#token=…` و`/reset-password#token=…` ثم ترسله في جسم العملية الصحيحة. نحتاج روابط متوافقة مع هذه الصفحات على دومين البيئة الصحيح، دون روابط `localhost` في الإنتاج أو تسريب الرموز إلى query strings أو سجلات التحليلات. هذه رموز الحساب فقط؛ **capability وclaim token لا يوضعان في الروابط**.

## 8. تقديم الفكرة والمستندات وClaim — ثوابت العقد

المطلوب تشغيل واختبار الموجود، لا تغيير البروتوكول لتجاوز خطأ في الواجهة:

| البند        | السلوك المطلوب الحفاظ عليه                                                                       |
| ------------ | ------------------------------------------------------------------------------------------------ |
| مسودة الزائر | تُنشأ عند الحاجة للرفع أو الإرسال، لا بمجرد فتح الصفحة؛ capability في الذاكرة وصلاحيتها 30 دقيقة |
| التصنيف      | قيم فعلية نشطة، وانتماء التصنيف الفرعي لأبيه؛ رفض علاقة غير صحيحة من الخادم                      |
| الميزانية    | قيمة عشرية كنص؛ USD حتى منزلتين وLYD حتى ثلاث؛ الصفر صالح؛ المجهولة بلا قيمة/عملة حسب المخطط     |
| المرفق       | ملف PDF أو DOCX اختياري واحد، حتى 10,485,760 بايت                                                |
| الحجز        | الحجم الفعلي وSHA-256 صغير الأحرف، وحجز صالح 10 دقائق ضمن صلاحية المسودة                         |
| الرفع        | bytes خام بنوع `application/octet-stream`، وليس multipart أو رابط تخزين عام                      |
| التزامن      | `If-Match` هو ETag الأب المقتبس حرفيًا؛ لا يُستبدل بإصدار المستند أو تشغيل AI                    |
| منع التكرار  | مفاتيح منفصلة للحجز والإرسال وClaim؛ المحاولة المطابقة تستخدم جسمها ومفتاحها وشرطها الأصلي       |
| نجاح الإرسال | حفظ دائم، مرجع حقيقي، ورد مؤكد من الخادم؛ لا نجاح محلي أو افتراضي                                |
| Claim        | رمز مستقل في الذاكرة؛ للعميل المؤكد المطابق، وصلاحية غير المستعمل 72 ساعة وفق العقد              |
| دوران الجلسة | يبطل تفويض مسودة الزائر؛ لا ينقل المرفقات تلقائيًا؛ إيصال الإرسال المكتمل يتبع Claim المستقل     |

يجب توفير دليل عمل التخزين الخاص والفاحص والعمال والتنظيف الدوري. يسمح العقد بإرسال مرفق اكتمل رفعه وهو `Quarantined` أو `Available`، لكنه لا يسمح بمرفق رفعه غير مكتمل أو مرفوض. تحليل AI يحتاج مستندًا `Available`. لا تنزيل للزائر، وتنزيل العميل لا يتجاوز فحص الحالة والتفويض.

رفع الملفات يتطلب تحققًا من النوع والمحتوى والحجم، وتخزينًا معزولًا عن الملفات العامة، وفحصًا قبل الإتاحة، وفق حدود العقد. مرجع إضافي للمراجعة: [OWASP — File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

الواجهة تفحص حالة المستند بعد 3 ثوانٍ ثم كل 5 ثوانٍ، بحد 12 محاولة تلقائية. انتهاء هذا الانتظار ليس فشلًا للعملية نفسها. نحتاج حالات نهائية واضحة ومراقبة تأخر العامل؛ ويمكن تحسين إعادة الاستعلام في الواجهة دون تمديد صلاحيات الزائر أو تجاوز الفحص.

استمرار Claim بعد إغلاق الصفحة أو إعادة تحميلها بالكامل غير متاح حاليًا لأن رمزه في الذاكرة. إذا كان مطلوبًا تجاريًا، نحتاج تصميمًا معتمدًا لاستمرارية آمنة من الخادم وعقدًا إضافيًا؛ لا نعالجه بتخزين الرمز في المتصفح أو ملكية مبنية على البريد/المرجع فقط. هذا تحسين منفصل عن الرحلة الحالية التي تبقى في التبويب الأصلي.

## 9. الذكاء الاصطناعي — اختياري

- Laravel يبقى البوابة الوحيدة. تفعيل المزود والنموذج والمفاتيح والتكاليف والعمال مسؤولية الخادم، ولا تُرسل مفاتيحه إلى Next.js أو المتصفح.
- المطلوب تقرير يحدد هل الخدمة مفعلة، والصلاحيات المتاحة للعميل، وحدود الطلبات والتكلفة، والحالات النهائية وأخطاء التعطل أو تحديد المعدل.
- تستخدم الواجهة حاليًا تحسين الوصف وتحليل المستند. العقد يتضمن أغراضًا إضافية، لكن وجودها لا يعني أن لها جميعًا أزرارًا أو رحلات مكتملة في الواجهة.
- إلغاء مهمة قيد الانتظار أو التنفيذ متاح بالفعل عبر `aiRunCancel`: `POST /api/v1/ai-runs/{aiRun}/cancellations`. يتطلب جلسة وصلاحية مناسبة وCSRF و`If-Match` و`Idempotency-Key`. يحتاج ربطًا في الواجهة عند إضافة زر الإلغاء؛ زر `Keep Mine / Dismiss` الحالي يرفض الاقتراح عبر عملية مختلفة ولا يلغي مهمة قيد التنفيذ.
- لا AI للزائر في العقد المعتمد. إن طُلب ذلك لاحقًا، يحتاج تصميم صلاحيات وميزانية ومكافحة إساءة وعقدًا جديدًا؛ لا نستدعي المزود مباشرة من الواجهة.
- عرض الاقتراح ثم تطبيقه صراحة، مع الحفاظ على وصف المستخدم. تعطل AI أو طابوره لا يمنع الإرسال العادي.
- الواجهة تستعلم عن تشغيل AI حتى 15 مرة بفاصل ثانيتين؛ تأخر العامل يتطلب متابعة حالة واضحة، وليس إبقاء اتصال HTTP مفتوحًا حتى ينتهي المزود.

## 10. بيئة التشغيل وSame-Origin

**المحلي المعتمد:** `https://localhost:8443`. يعمل التوجيه بالفعل. لا نحتاج عنوان API خارجيًا منفصلًا ولا CORS لتشغيله.

| المسار الذي يطلبه المتصفح                         | الخدمة المسؤولة                   |
| ------------------------------------------------- | --------------------------------- |
| صفحات الموقع و`/_next/*` والأيقونات وصفحات الحساب | Next.js للموقع                    |
| `/api/v1/*`                                       | Laravel وفق العمليات المعتمدة     |
| `/sanctum/*`                                      | Laravel/Sanctum                   |
| `/admin` وعائلته                                  | مشروع لوحة المدير المنفصل         |
| مسارات الصحة الحالية                              | المعالجات المعتمدة في بيئة الخادم |

في Staging والإنتاج نحتاج نفس نموذج الأصل الموحد على الدومين المعتمد، وشهادة موثوقة، وتوجيهًا صريحًا يحتفظ بـOrigin وCSRF والمصادقة. لا تُنسخ قواعد `localhost:8443` حرفيًا إلى الإنتاج، ولا تُضاف أصول عشوائية أو تُفتح منافذ قواعد البيانات والتخزين للمتصفح.

نحتاج كذلك:

- تشغيل نسخة مبنية من Next.js وخدمات Laravel بإعدادات الإنتاج، وإعادة التشغيل التلقائي والتحقق من الصحة؛ لا `next dev` في الإنتاج.
- بقاء HTTP uploads الخام والكوكيز وETag و`If-Match` و`Idempotency-Key` و`X-Request-ID` و`Retry-After` سليمة عبر الوكيل.
- الإبقاء على حد ملف 10 MiB وحد ingress الحالي المناسب له وهو 12 MiB للمسارات المعنية، دون رفع شامل غير مدروس.
- ملفات ثابتة ذات أسماء مبنية على المحتوى، وضغط HTTP، ووقت انتظار وحجم طلب محددين، وعدم فرض CSP الخاصة بـJSON على صفحات HTML.
- إذا تعددت نسخ Next.js، استخدام نفس ناتج البناء ومعالجة اتساق الكاش والتحديثات والأصول أثناء النشر. تفاصيل التشغيل المرجعية: [Next.js — Self-hosting](https://nextjs.org/docs/app/guides/self-hosting).
- تحديد الدومين النهائي، والمنطقة المستهدفة، وموارد CPU/RAM والتخزين، وحجم الزيارات والرفع المتوقع؛ لا يمكن ضمان الأداء باختيار رقم موارد دون هذه المعلومات.

## 11. متطلبات الأداء القابلة للقياس

### أهداف مبدئية للاتفاق، وليست نتائج تحققت

| القياس                                 | الهدف المقترح                        | كيفية التحقق                                              |
| -------------------------------------- | ------------------------------------ | --------------------------------------------------------- |
| قراءة البيانات العامة الصغيرة          | p95 ≤ 300ms                          | عند ingress في البيئة المستهدفة؛ فصل الكاش البارد والدافئ |
| العمليات القصيرة للحفظ والقراءة الخاصة | p95 ≤ 800ms                          | دون زمن رفع bytes أو انتظار البريد/الفحص/AI               |
| أخطاء 5xx                              | أقل من 0.5% أثناء الحمل المتفق عليه  | فصل أخطاء التحقق و429 المقصودة عن أخطاء الخادم            |
| حجم صفحة قائمة معرض من 12 عنصرًا       | ≤ 100 KiB JSON مضغوط كهدف أولي       | دون الصور والوصف الكامل والمعارض غير المطلوبة             |
| حداثة نشر المعرض                       | ظهور التغيير خلال 60 ثانية كهدف أولي | قياس نشر/تعديل/إلغاء نشر مع إبطال الكاش                   |
| تجربة المتصفح                          | LCP ≤ 2.5s، INP ≤ 200ms، CLS ≤ 0.1   | عند المئين 75، منفصلًا للهاتف والكمبيوتر                  |

الأرقام الخاصة بـAPI أعلاه مقترحات للمشروع تحتاج اعتماد الفريق وقياسًا على الخادم المستهدف. لا تشمل وعودًا غير مقاسة. حدود تجربة المتصفح مصدرها [Core Web Vitals](https://web.dev/articles/vitals)، وهي مسؤولية مشتركة بين الواجهة والخادم والشبكة.

### التخزين المؤقت وحجم البيانات

- بيانات معرض عامة مصغرة للقائمة، وعملية تفاصيل منفصلة، وترقيم وفلاتر في الخادم. لا تحميل كل المشاريع أو كل الصور لحساب عدد العناصر.
- سياسة Cache-Control موثقة للقراءات العامة الجديدة. يمكن بدء كاش قصير للمعرض وإحصاءات مجمعة أطول نسبيًا بعد اعتماد حداثة البيانات وإبطال النشر. الصور ذات المعرف/البصمة الجديدة يمكن تخزينها أطول.
- لا تخزين مشترك لردود الحسابات أو الطلبات الخاصة أو CSRF أو عمليات الكتابة. لا تسمح قواعد CDN بعرض بيانات مستخدم لآخر.
- العميل المركزي الحالي يستخدم `cache: no-store`. إضافة كاش للموارد العامة تحتاج تعديلًا محددًا في الواجهة والعقد/الرؤوس؛ لا تغيّر سياسة كل العمليات مرة واحدة. دعم 304، إذا اختير، يحتاج معالجة صريحة في العميل.
- البيانات العامة القابلة للتخزين يجب ألا تحتوي بيانات جلسة أو تتغير بحسب المستخدم. تُختبر إعدادات `Vary` و`Set-Cookie` ومفاتيح الكاش قبل تفعيل CDN.
- تحويل الصور وإنشاء المصغرات مرة واحدة، وتقديم حجم مناسب للشاشة بدل إعادة معالجة الأصل الثقيل في كل مشاهدة.

### قاعدة البيانات والمهام الخلفية

- تقرير عن الاستعلامات البطيئة وخططها على حجم واقعي، مع فهارس مبنية على أنماط الفلترة والملكية والترتيب الفعلية، ومنع N+1. لا نطلب إضافة فهارس عشوائية.
- الإحصاءات الثقيلة لا تُحسب لكل زائر. الكتابات الحساسة تبقى معاملات صحيحة؛ عدد العمال والاتصالات يضبط وفق الموارد والقياس.
- فصل أحمال البريد والمستندات وAI بحيث لا يوقف تعطل أحدها استقبال الأفكار. Postgres يبقى مصدر الحقيقة وفق المعمارية الحالية، وRedis ليس بديلًا عن السجلات الدائمة.
- محاولات محدودة، وتأخير بين المحاولات، ورصد للوظائف الفاشلة وعمر أقدم مهمة. ضبط timeout العامل أقصر من `retry_after` حيث ينطبق، مع احترام آلية المطالبات الدائمة الحالية. مرجع: [Laravel 13 — Queues](https://laravel.com/framework/docs/13.x/queues).

### تقرير الحمل المطلوب

يتضمن مواصفات البيئة، وإصدارات البناء، وحجم البيانات، والمنطقة، وعدد المستخدمين ومعدل الطلبات وخليطها، ومدة القياس، وp50/p95/p99، والأخطاء، وCPU/RAM واتصالات قاعدة البيانات وعمق الطوابير. يبدأ الفريق بحمل ممثل للزيارات المتوقعة ثم يبين هامش الزيادة ونقطة التشبع.

تُختبر العمليات العامة والخاصة كلٌ وفق حدودها. لا نعطّل Rate Limits أو CSRF أو الفحص لإنجاح الأرقام، ولا نعتبر نتيجة حمل محلي شهادة لخادم الإنتاج. بعد معرفة الحمل المستهدف، تعتمد حدود الخدمة وسعة الخادم نهائيًا.

## 12. المراقبة والاستمرارية والبيانات

- فحوص جاهزية وحيوية موثقة، وتنبيهات لانقطاع API والبريد والفحص وتراكم الطوابير وقرب امتلاء التخزين.
- ربط سجلات التشغيل بـ`X-Request-ID` دون تسجيل كلمات المرور أو الرموز أو capability أو claim token أو أجسام المستندات والطلبات الحساسة.
- التعامل مع `400/401/403/404/409/412/413/415/422/428/429/500/503` وفق ErrorEnvelope، وإرجاع أخطاء آمنة دون الاستثناءات الداخلية.
- نسخ احتياطية متسقة لقاعدة البيانات والملفات الخاصة، وتشفير وصلاحيات محدودة، واختبار استعادة فعلي. يحدد الفريق RPO/RTO للاعتماد مع صاحب المشروع؛ وجود نسخة احتياطية وحده لا يثبت إمكانية الاستعادة.
- تعليمات نشر وترحيل وفحص وتراجع لا تمحو تاريخ الطلبات أو بيانات الزائر؛ لا تُستخدم إعادة تهيئة قاعدة البيانات كحل للنشر.
- بيانات إنتاج حقيقية معتمدة للمعرض والتصنيفات ووسائل التواصل، وإزالة بيانات الاختبار من العرض العام. سياسة احتفاظ وموافقة على نشر الصور ومحتوى العملاء يحددها صاحب المشروع والفريق المختص.

## 13. ما يبقى على الواجهة، ولا يُطلب من Backend وحده

1. استبدال موصل معرض Dashboard بالعمليات العامة الجديدة، واستهلاك الترقيم والصور والتفاصيل والكاش.
2. تحويل Contact من حفظ مسودة محلية إلى إرسال فعلي وحالات نجاح/فشل مبنية على الرد؛ ربط الإحصاءات إذا اعتُمدت API لها.
3. إعادة توليد الأنواع من العقد الجديد واختبار توافق الـ31 عملية الموجودة، دون تغيير مصدر الحقيقة يدويًا.
4. مراجعة التعامل مع 401 و403: الكود الحالي يمرر بعض 403 المصادق عليها إلى منطق انتهاء الجلسة؛ نقص الصلاحية لا ينبغي تفسيره تلقائيًا بأنه انتهاء تسجيل الدخول. لا يُطلب من الخادم إرجاع 200 لتجاوز ذلك.
5. ربط حالة الحساب في التنقل، وإكمال تجربة أخطاء التأكيد والمهل والاستعلام البطيء، والتحقق من الهاتف/العربية والكيبورد والموبايل.
6. صفحات `/portal/*` ما زالت تحتوي بيانات/واجهات تجريبية؛ تُحجب من الإطلاق أو تُستكمل كمرحلة منفصلة. البديل الحقيقي الحالي هو `/my-requests`. توجد أصلًا عمليات `projectCustomerList` و`projectCustomerDetail` وتحديثات ومراحل وإشعارات في العقد؛ لا تُصنف كلها كنواقص Backend.
7. صفحات معاينة `/admin/*` داخل مشروع الموقع ليست لوحة المدير الفعلية. في ingress يبقى `/admin` موجهًا للمشروع المنفصل، ولا تُعرض معاينات الموقع باعتبارها نظام إدارة مكتملًا.
8. إعداد sitemap والروابط canonical وmetadata للدومين النهائي، وعدم فهرسة صفحات الحساب والطلبات الحساسة. `robots.txt` و`noindex` ليسا بديلًا عن التفويض.
9. تحسين الصور وتحميل JavaScript والكاش وقياس Web Vitals ثم اختبار E2E. اكتمال Backend وحده لا يضمن أعلى أداء للمتصفح.

الصفحات التعريفية مثل About وServices وSolutions وIndustries يمكن أن تبقى محتوى ثابتًا سريعًا. لا تحتاج CMS أو API لمجرد تشغيلها؛ تُضاف إدارة محتوى فقط إذا أراد صاحب المشروع تحريرها من لوحة المدير. المحادثات المباشرة وAI للزائر واستعادة Claim بعد إغلاق التبويب إضافات مستقلة، وليست مفترضة ضمن نطاق الإطلاق الحالي.

## 14. اختبارات قبول مشتركة قبل الإطلاق

| الرحلة                                           | النتيجة المطلوبة                                                                       |
| ------------------------------------------------ | -------------------------------------------------------------------------------------- |
| زائر دون مرفق                                    | تصنيفات حقيقية، مراجعة، إرسال واحد، مرجع حقيقي                                         |
| زائر مع PDF ثم DOCX في طلب مستقل                 | hash/bytes صحيحة، حالة فحص حقيقية، إرفاق وإرسال وفق العقد                              |
| ملف غير صالح أو كبير أو مرفوض                    | رفض مفهوم؛ لا إتاحة ولا نجاح وهمي                                                      |
| عميل يسجل ويؤكد بريده ويسجل الدخول               | ملف صحيح وبيانات اتصال للعرض فقط وإرسال ومتابعة طلبه                                   |

| حساب آخر يحاول الوصول أو Claim                   | رفض عام دون كشف بيانات صاحب الطلب                                                      |
| capability منتهية أو جلسة دارت أو claim غير صالح | فشل آمن؛ لا تجاوز حماية أو فقد صامت للبيانات المدخلة                                   |
| رد الإرسال ضاع بعد الحفظ                         | إعادة مطابقة بنفس المفتاح والجسم والشرط، دون طلب مكرر                                  |
| ETag قديم أو ناقص                                | 412/428 وحفظ إدخال المستخدم، دون كتابة فوق بيانات أحدث                                 |
| تحديد معدل أو تعطل AI/البريد/عامل                | احترام Retry-After، وحالة صادقة، وعدم تعطيل ما يمكن تشغيله بأمان                       |
| المعرض                                           | فلترة وترقيم وتفاصيل وصور صحيحة؛ إلغاء النشر يزيل الوصول العام وفق السياسة             |
| التواصل                                          | حفظ دائم واحد وإشعار قابل للتتبع؛ اختبار الفشل وإعادة المحاولة                         |
| نشر نسخة جديدة                                   | لا ملفات JavaScript مفقودة ولا كسر للجلسات أو مسارات البريد                            |
| جهاز هاتف وكمبيوتر                               | اكتمال النموذج والرفع والمراجعة والحساب دون تجاوز أفقي، مع labels وfocus وإعلانات حالة |

تُستخدم هويات وملفات اصطناعية، وخادم حقيقي، وأصل موحد، وشهادة موثوقة. لا تُستبدل APIs الحرجة ببيانات Mock في اختبار القبول، ولا تُستخدم حسابات العملاء الحقيقية. اختبارات انتهاء المدد تستخدم آلية اختبار معتمدة في بيئة معزولة دون تغيير أعمار الرموز في الإنتاج.

## 15. ترتيب التسليم ونموذج رد الفريق

**الدفعة الأولى:** تأكيد البيئة الموحدة والبريد والتصنيفات والملفات والملف الشخصي، ثم إنهاء اختبارات الحساب والإرسال وClaim الحالية.

**الدفعة الثانية:** عقد وتنفيذ معرض المشاريع والتواصل؛ وإحصاءات عامة إذا اعتُمدت. يليها ربط الواجهة واختبارات الحالات العامة.

**الدفعة الثالثة:** اعتماد نشر Staging والإنتاج والأداء والمراقبة والاستعادة، ثم تفعيل AI عند جاهزيته. لا تُنقل معايير الإنتاج إلى مجرد نجاح اختبار محلي.

يرجى إعادة هذا الجدول مكتملًا مع الروابط والملفات، دون بيانات سرية:
